## เกิดอะไรขึ้น

<div class="split">
<div class="prose">

วันที่ 19 พฤศจิกายน 2569 หน้าแรกของ php.net ประกาศออกพร้อมกัน 5 รุ่นครับ

PHP 8.6.0 คือรุ่นหลักตัวจริง ส่วน 8.5.13, 8.4.28, 8.3.37 และ 8.2.36 ทีม PHP เขียนไว้ชัดว่า "This is a security release" แปลว่าเป็นรุ่นแก้ช่องโหว่ และแนะนำให้คนที่ใช้สายนั้นอัปเดต

ใน ChangeLog ของ php.net รุ่นความปลอดภัยทั้งสี่รุ่นลงวันที่ 19 พ.ย. 2569 เหมือนกัน ส่วน 8.6.0 ก็มีรายการแก้ช่องโหว่ชุดเดียวกันอยู่ในบันทึกการเปลี่ยนแปลง

เรื่องนี้ต่อเนื่องมาจาก PHP2Shell เมื่อ 21 ต.ค. ครับ (อ่านได้ใน <a href="/news/php2shell/">ข่าวก่อนหน้า</a>) ในชุดนี้มี 2 ช่องโหว่ที่ GitHub ระบุว่าเกิดจากการแก้ CVE-2026-109619 ตัวเดิมที่ยังไม่ครบ

## ช่องโหว่ Critical ทั้ง 7 รายการ

<div class="prose">

ThaiCERT นับ Critical ไว้ 7 รายการ ตรงกับหน้า advisory ของ php-src บน GitHub ครับ ครบ 7 รายการ ระดับ Critical และได้ CVSS v4 9.2 ทุกตัว

แต่คะแนนเท่ากันไม่ได้แปลว่าเสี่ยงเท่ากันครับ แต่ละตัวมีเงื่อนไขของตัวเอง บางตัวกระทบแค่ PHP 8.5 เลยเรียงเป็นการ์ดไว้ให้เช็กทีละรายการ

<div class="news-cards">
<div class="news-card is-bad"><b>CVE-2026-129289 · PHP-FPM request smuggling</b><span class="news-pill">8.2 ถึง 8.5</span> PHP ไม่ทิ้งข้อมูลส่วนที่ยังไม่ได้อ่านของคำขอ HTTP ก่อนเอาการเชื่อมต่อ FastCGI ที่ค้างไว้ไปใช้ต่อ ผู้โจมตีที่ไม่ต้องล็อกอินจึงแอบแทรกคำขอใหม่เข้าไป ข้ามเว็บเซิร์ฟเวอร์ด้านหน้า แล้วสั่งรันโค้ด PHP ได้ ThaiCERT ระบุว่าต้องเปิดใช้การเชื่อมต่อค้างไว้ (เช่น NGINX ที่ตั้ง fastcgi_keep_conn on) และแอปต้องเปิด php://input แล้วอ่านไม่จบ ThaiCERT แนะนำให้แก้ตัวนี้ก่อน</div>
<div class="news-card is-bad"><b>CVE-2026-129474 · Use-after-free ตอนเก็บ backtrace</b><span class="news-pill">เฉพาะ 8.5</span> เกิดตอน PHP เก็บอาร์กิวเมนต์ของเมธอดที่เรียกผ่าน __call() หรือ __callStatic() ตอนเกิด fatal error คำขอที่สร้างมาเฉพาะอาจรันโค้ดด้วยสิทธิ์ของ PHP worker ได้ เงื่อนไขคือ fatal_error_backtraces=1 (ค่าเริ่มต้นของ PHP 8.5) และ zend.exception_ignore_args=0 ส่วนไฟล์ php.ini-production ตั้ง zend.exception_ignore_args เป็น 1 ไว้ จึงกันทางนี้อยู่แล้ว</div>
<div class="news-card is-warn"><b>CVE-2026-129182 · Use-after-free ของ last_fatal_error_backtrace</b><span class="news-pill">เฉพาะ 8.5</span> เกิดจากการแก้ CVE-2026-109619 ที่ยังไม่ครบ ค่าที่ควรถูกล้างทิ้งหลังจบคำขอกลับถูกสร้างขึ้นใหม่ แล้วคำขอถัดไปใน worker ตัวเดิมไปอ่านต่อ ต้องมีการตั้งค่าเฉพาะ เช่น ตั้ง max_memory_limit ไว้ทั้งระดับ global และระดับ path ThaiCERT ระบุว่ายังไม่มีการสาธิตว่ารันคำสั่งผ่านทางนี้ได้</div>
<div class="news-card is-bad"><b>CVE-2026-129496 · Use-after-free ของ timezone cache</b><span class="news-pill">8.2 ถึง 8.5</span> เกิดเมื่อมีข้อความเตือนตอนเริ่มระบบถูกเขียนลงไฟล์ error log แล้วมีข้อความเตือนอีกครั้งในคำขอแรกของ worker ตัวใหม่ อาจทำให้ worker ล่ม หรือถูกรันโค้ดได้ ThaiCERT ระบุว่ากระทบ PHP-FPM, Apache mod_php และ CGI ที่เป็น non-thread-safe build</div>
<div class="news-card is-warn"><b>CVE-2026-129481 · Use-after-free ตอนปิด session</b><span class="news-pill">8.3 ขึ้นไป</span> เกิดจากการแก้ CVE-2026-109619 ที่ยังไม่ครบอีกตัว คำขอถัดไปใน worker ตัวเดิมอาจปล่อยหน่วยความจำที่ค้างอยู่ซ้ำอีกรอบ GitHub ระบุว่า PHP 8.2 ไม่มีฟิลด์ที่เป็นต้นเหตุ จึงไม่โดนตัวนี้</div>
<div class="news-card is-warn"><b>CVE-2026-126714 · ไฟล์ session เขียนไม่จบ</b><span class="news-pill">8.2 ถึง 8.5</span> ถ้าตัวจัดการ session แบบ files (ค่าเริ่มต้น) เขียนไฟล์ไม่จบ ไฟล์จะมีข้อมูลของสอง session ปนกัน ผู้โจมตีอาจทำให้ PHP deserialize วัตถุที่ตัวเองสร้างขึ้นได้ แต่ต้องมี gadget chain ในแอปด้วยถึงจะรันโค้ดได้</div>
<div class="news-card is-warn"><b>CVE-2026-115560 · session serializer ไม่ตรงกัน</b><span class="news-pill">8.2 ถึง 8.5</span> ฟีเจอร์ session upload progress เขียนข้อมูลด้วยรูปแบบหนึ่ง แต่ถูกอ่านกลับด้วยอีกรูปแบบ เงื่อนไขคือต้องเปิดฟีเจอร์นี้ ใช้ serializer แบบ php_binary หรือ php_serialize และมี gadget chain ในแอป GitHub ระบุว่ารุ่นเก่าที่หมดซัพพอร์ตแล้วอาจโดนด้วย</div>

ใช้ PHP สายไหนอยู่ ก็อัปเป็นเลขล่าสุดของสายนั้น ถ้ายังไม่พร้อมก็ไม่ต้องข้ามสาย ส่วน 8.6.0 เป็นรุ่นหลักใหม่ มีทั้งฟีเจอร์ใหม่และของที่เลิกใช้ ผมแนะนำให้อ่านคู่มือย้ายรุ่นก่อนครับ

## ที่เหลืออีก 10 รายการ

<div class="prose">

นอกจาก 7 ตัวข้างบน รุ่นเดียวกันนี้ยังปิดช่องโหว่ระดับ High อีก 4 รายการ และ Medium อีก 6 รายการ

ตัวที่น่าสนใจคือ CVE-2026-129291 ที่ PHP-FPM อาจถูกหลอกให้ใช้หน่วยความจำที่ถูกปล่อยไปแล้ว ทำให้ผู้โจมตีที่รันโค้ดใน worker ได้อยู่แล้ว ยกสิทธิ์ตัวเองขึ้นเป็นสิทธิ์ของ FPM master ซึ่งมักรันเป็น root (ต้องเปิด catch_workers_output) ตัวนี้ต่างจาก 7 ตัวแรกที่เข้ามาจากข้างนอก เพราะผู้โจมตีต้องรันโค้ดบนเครื่องได้ก่อน

อีก 3 รายการระดับ High คือ ไฟล์ PHAR ข้ามการตรวจลายเซ็น OpenSSL ได้ (CVE-2026-128090), URL แบบ HTTPS หรือ FTPS ที่สะกดตัวพิมพ์เล็กใหญ่ปนกัน ทำให้ข้อมูลถูกส่งเป็นข้อความธรรมดาไม่เข้ารหัส (CVE-2026-128064) และเซิร์ฟเวอร์ HTTP ที่ส่งเฮดเดอร์แบบพับบรรทัดมาเยอะ ๆ ทำให้ PHP กิน CPU หนัก (CVE-2026-127960)

## ถ้ายังอัปไม่ได้ทันที

<div class="prose">

ThaiCERT รวมวิธีลดความเสี่ยงชั่วคราวไว้ในประกาศ และบางข้อ GitHub ก็เขียนไว้ในหน้า advisory ครับ ทั้งหมดนี้แค่ช่วยลดความเสี่ยง ไม่ได้กันได้ทุกช่องโหว่ และ ThaiCERT ย้ำให้ลงรุ่นที่แก้แล้วโดยเร็วที่สุด

<ol class="news-steps">
<li><b>กันช่องโหว่ backtrace ของ PHP 8.5</b>ตั้ง zend.exception_ignore_args=1 หรือ fatal_error_backtraces=0 ในค่าที่ worker ใช้งานจริง รวมถึง pool ของ PHP-FPM แล้วรีสตาร์ต worker แก้แค่ค่าของ CLI ไม่พอ</li>
<li><b>ปิด session upload progress</b>ตั้ง session.upload_progress.enabled=0 ในค่าระดับผู้ดูแลระบบ ใช้ ini_set() ในแอปไม่พอ ช่วยกัน CVE-2026-126714 และ 115560</li>
<li><b>แก้ต้นเหตุของคำเตือนตอนเริ่มระบบ</b>เช่น date.timezone ที่ตั้งผิด หรือส่ง error log ไป syslog แทนไฟล์ ช่วยกัน CVE-2026-129496</li>
<li><b>ลดอายุของ worker ชั่วคราว</b>ThaiCERT เสนอให้ตั้ง pm.max_requests=1 บน PHP-FPM สำหรับ CVE-2026-129481 แต่จะกระทบประสิทธิภาพ</li>
<li class="is-key"><b>ตรวจให้ทั่ว ไม่ใช่แค่เซิร์ฟเวอร์หลัก</b>ThaiCERT ให้สำรวจทุกที่ที่มี PHP ทั้ง CMS, container image และอุปกรณ์ที่ฝัง PHP มาในตัว เพราะ PHP ที่ติดมากับผลิตภัณฑ์ของคนอื่น ต้องรอเจ้าของผลิตภัณฑ์ออกแพตช์</li>
</ol>

## ThaiCERT ว่าอย่างไร และสิ่งที่ยังไม่พบ

<div class="prose">

ThaiCERT ออกประกาศ 2 ฉบับเมื่อ 20 พ.ย. 2569 ฉบับหนึ่งอธิบายช่องโหว่ทีละรายการพร้อมวิธีลดความเสี่ยง อีกฉบับเป็นประกาศเตือนเลขที่ 640/69 แบบสรุปสั้น ทั้งสองฉบับนับ Critical ไว้ 7 รายการ ตรงกับ php.net และ GitHub

ฉบับที่สองยังเทียบกับ PHP2Shell เมื่อเดือนที่แล้วว่า ช่องโหว่ชุดนี้ส่วนใหญ่ต้องอาศัยการตั้งค่าที่ไม่ใช่ค่าเริ่มต้น หรือสภาพแวดล้อมเฉพาะ จึงน่าจะไม่ถูกโจมตีเป็นวงกว้างได้ง่ายเท่า แต่ก็ย้ำให้รีบอัป

ทั้งหน้า php.net, ChangeLog, หน้า advisory บน GitHub และประกาศของ ThaiCERT 2 ฉบับ ยังไม่มีที่ไหนบอกว่าช่องโหว่ชุดนี้ถูกโจมตีจริงแล้ว และผมยังไม่พบรายงานผู้เสียหายในไทยครับ
